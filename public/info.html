How INTLLM works

INTLLM is a local-first AI runtime: a FastAPI backend, a web UI, layered memory, tools and an OpenAI-compatible local API built around local models served by Ollama. It is the orchestration layer around the model — not a model itself.

01

Overview

A normal local model setup is just model → prompt → response. Such a model has no memory of your context, no access to current information, no safe tool access and no API surface your other tools can use.

INTLLM does not retrain the base model for every new fact. Instead it supplies the surrounding environment: layered memory stored in local PostgreSQL with pgvector, optional live web retrieval with source attribution, a tool gateway that mediates browser and filesystem access, and a local OpenAI-compatible API with its own key system — all while user responses always keep priority over background work.

  • Local first — backend, database, memory, models and UI run on your machine; the API binds to 127.0.0.1 by default.
  • User first — background maintenance yields resources whenever interactive work needs them.
  • Model agnostic — the model list comes from your Ollama inventory; nothing is hardcoded.
  • Transparent — dependency state is reported honestly (running / stopped / unavailable / misconfigured); nothing is fabricated.

03

Layered memory

Relevant memory is retrieved and added to the model context during chat; retrieved memory is labelled in the response. Background maintenance keeps indexes and freshness current — it is knowledge maintenance, not model retraining.

L0

Flash Brain

A fast routing/index layer over memory — a vector index plus keywords that answers: is useful memory available, where is it, how fresh, how confident? It is not the full knowledge store.

L1

Hot Cache

Short-lived cache of recently useful query results (30-minute default TTL). A promoted result avoids all vector work on repeat lookups; confident and fresh top matches get promoted automatically.

L2

Secondary Brain

The durable store of curated, verified knowledge in PostgreSQL + pgvector: compact facts, workflows, lessons and preferences with provenance, confidence and freshness policies (TTLs from ~1 year down to 6 hours).

04

Tools, browser & internet

The model never directly owns OS or browser privileges. Every tool call passes through one gate: validation → policy → permission → execution → sanitization. Retrieved web content is treated as data, not instructions, and non-public URLs are rejected by SSRF guards.

Live web retrieval (DuckDuckGo by default, SearXNG optional) is opt-in per request — nothing goes to the internet automatically. Sources are never fabricated; when a provider is unreachable you get an explicit unavailable state. The browser agent is optional (Playwright) and reported as unavailable when not installed.

05

Model runtime — Ollama

All inference happens through your local Ollama daemon (http://127.0.0.1:11434 by default). INTLLM detects the daemon, lists, pulls and deletes models, streams chat and reports health — and never bundles or silently installs Ollama itself.

The model list comes from your actual Ollama inventory — Qwen, Llama, DeepSeek, Gemma, Mistral and other compatible families work in principle. If Ollama is unavailable, API calls fail with a clear 503 service_unavailable — never fabricated output.

06

Hardware tiers

INTLLM ranks installed models against your detected CPU, RAM and GPU/VRAM budget using three recommendation tiers. They are recommendation categories, not strict restrictions — what matters is fitting a model's memory requirement inside your VRAM/RAM budget.

TierTypical hardwareGuidance
Potato Low-end, iGPU, older machines Small quantized models, low memory usage, smaller context.
Nutral Balanced / mid-range 7B–14B-class options where hardware permits, moderate context.
I Paid for My Whole PC High-end Larger models, larger context, heavier agent workflows.

Hardware detection uses psutil and nvidia-smi when present; values that cannot be detected are shown as N/A rather than invented.

07

OpenAI-compatible local API

Point any OpenAI-compatible client at http://127.0.0.1:8000/v1 with an INTLLM API key. Requests route through the same orchestrator as the UI — memory and security aware, not a bypass.

Endpoints 
GET  /v1/models
GET  /v1/models/{model}
POST /v1/chat/completions          # stream: false (JSON) | true (SSE)

INTLLM-specific request fields: intllm_use_brain (include long-term memory, default on) and intllm_use_web (enable live retrieval for this request, default off). API keys are generated locally, stored as salted scrypt hashes, shown exactly once and revocable at any time.

Endpoints that are not implemented — embeddings, responses, audio, images, files, fine-tuning — are not exposed and not documented.

08

Security & privacy

INTLLM is designed to keep data and execution local by default and to make every privileged action explicit — but local does not automatically mean safe; tool permissions and dependencies remain the user's responsibility to configure.

  • Local API bound to 127.0.0.1 by default; network exposure is an explicit opt-in.
  • API authentication with salted scrypt key hashes, one-time reveal and revocation.
  • Secrets redacted from logs; no secrets in frontend bundles or release artifacts.
  • No hidden cloud sync, telemetry pipeline or account system — conversations, memory and keys live in your local PostgreSQL.
  • Live web retrieval is off by default and enabled per request; model inference never leaves the machine.

Project status & roadmap

The current release implements the full local runtime: FastAPI backend, React web UI, PostgreSQL + pgvector memory, Ollama orchestration, tool gateway, OpenAI-compatible API and Windows packaging. Planned work is specified but not shipped — and never presented as such:

  • Automatic post-response memory learning (candidate → verify → promote)
  • Duplicate detection, memory compression and failure analysis as background jobs
  • Richer browser workflows (form filling, structured page interaction)
  • Memory export/import, additional model adapters, better multi-runtime routing

FAQ

Does INTLLM run locally?
Yes. The backend, database, memory, models and UI run on your machine. The API binds to 127.0.0.1 by default.
Does INTLLM use Ollama?
Yes — Ollama is the core local model runtime. INTLLM detects the daemon, lists/pulls/deletes models and streams inference through it. Ollama is installed separately; INTLLM never bundles or silently installs it.
Does INTLLM require internet?
No. It works fully offline except for features you explicitly enable: live web retrieval is opt-in per request. Model inference and memory are local.
Where is my data stored?
In your local PostgreSQL database (with pgvector), on your machine. There is no cloud sync and no INTLLM-hosted storage. Windows installs keep runtime data in %LOCALAPPDATA%\INTLLM.
What models can I use?
Whatever your local Ollama installation reports — e.g. Qwen, Llama, DeepSeek or other compatible families. INTLLM does not hardcode or invent models; feature support varies per model.
Does INTLLM retrain models?
No. INTLLM performs low-priority background knowledge maintenance — verification, freshness, index updates, cache cleanup. It never retrains Ollama model weights.
What hardware do I need?
INTLLM gives recommendation tiers — Potato, Nutral, I Paid for My Whole PC — based on detected CPU/RAM/GPU/VRAM. They are recommendations, not restrictions; what matters most is fitting the model's memory requirement within your VRAM/RAM budget.
How do I install INTLLM?
Windows: irm https://intllm.vercel.app/install.ps1 | iex · Linux/macOS: curl -fsSL https://intllm.vercel.app/install.sh | bash. You will also need Ollama and PostgreSQL with pgvector installed separately. See the install guide.
